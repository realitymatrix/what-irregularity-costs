The result

GPU language comparisons are almost always run on tiled dense linear algebra, where every toolchain is good and the differences are small. We implement the same hash-blocked TSDF fusion kernel five times and measure it on a workload with the opposite character: an open-addressed hash table with compare-exchange insertion, data-dependent per-lane probe depth, and contended scatter.

Why, not just how much

Triton: two costs that compound

There is no per-lane early exit, so a probe loop runs to a compile-time bound and every lane pays worst-case depth. And tl.atomic_cas takes no mask, unlike tl.atomic_add, so lanes that have already resolved must be aimed at a scratch address. That scratch structure has no counterpart in the CUDA implementation, and sizing it badly costs a factor of twenty — while also silently destroying the kernel's ability to use additional streaming multiprocessors, a failure invisible on a single GPU.

Stronger than any ratio: Triton cannot express an unbounded probe at all. The bound must be a compile-time constant, and a bound small enough to compile is small enough to silently lose data at load factors CUDA C++ handles exactly.

Rust: the safe construct is the expensive one

Rust's gap was invisible to every instruction count we could take. The Rust kernel issues fewer branches, fewer memory operations and 12% fewer dynamic compare-exchanges, from a smaller register budget, at identical occupancy — and was still slower. It does less work, more slowly.

Hardware counters found it in L1 residency: identical requests, but 1.70× the sectors pushed to L2 and an L1 hit rate of 28.9% against 55.9%.

A GPU-scope atomic load must be coherent across SMs. No NVIDIA L1 is coherent across SMs. So the type-correct way to read a shared location bypasses the cache on every access — relaxed removes ordering, not coherence.

Replacing two such reads with plain loads, correct because the algorithm rather than the memory model provides the guarantee, restores every counter to parity. Nothing in the source, the PTX, the machine code or the occupancy reveals this; it is visible only in where the data is permitted to live.

What we got wrong

Roughly a dozen measurement errors were caught during this work. Three would have produced a reversed or null conclusion rather than a wrong magnitude, and two survived long enough to be written up:

  • A 40% workload asymmetry made the slower arm look 2× faster.
  • A device axis was silently fake: one arm's loader pinned device zero for the whole process, so a two-GPU sweep reported a clean null while the second card sat idle at 8 W. Nothing in the timings looked anomalous.
  • A single measurement pass was not reproducible, and no within-pass statistic separates that case from ordinary variance.

All three were failures of comparability, not precision. None would have been caught by more repetitions or tighter error bars. Two published figures were also corrected: Triton's gap from 73× to 17.9×, mostly our own badly-sized workaround rather than the language.

A defect found along the way

In the version of cuda-oxide used here, the scoped atomic load and store could not be called at all. Both lowered to LLVM IR that libNVVM rejects, so every call failed the backend verifier in the build mode that produces real kernels — with an error naming an LLVM basic block rather than the offending line of Rust. The project's own atomics example does not build in that mode.

The underlying PTX instructions have existed since sm_70. Fix contributed upstream as NVlabs/cuda-oxide#695, with tests, a regression example, and the CI registration whose absence let the defect survive.
